# UI 文案、帮助内容与社交帖子

## 界面文字

用户看界面文字时，正在做别的事。他们不是来读的，是来完成一件事的。界面文字的工作，是让他们不停下来就能继续。

几份公开的好参照：

- [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/)：把自己的声音概括为 warm and relaxed、crisp and clear、ready to lend a hand。
- [Google developer documentation style guide](https://developers.google.com/style)：技术文档和界面文字的细节规范。
- [Mailchimp Content Style Guide](https://styleguide.mailchimp.com/)：讲清楚了不同情境下语气怎么变。
- Torrey Podmajersky 的 *Strategic Writing for UX* 和 Kinneret Yifrah 的 *Microcopy: The Complete Guide*：专讲界面上的短文字。

## 按位置写

| 位置 | 要传达 | 常见错误 |
|---|---|---|
| 按钮 | 点了会发生什么 | 用“确定”“提交”掩盖了删除、付款、发送 |
| 表单说明 | 要填什么、什么格式、为什么要 | 出错后才告诉格式要求 |
| 错误提示 | 发生了什么，用户能怎么办 | “出了点问题”；或者乱归因到网络 |
| 空状态 | 为什么这里是空的，可以做什么 | 让用户以为是系统坏了 |
| 成功提示 | 完成了什么，具体的 | 把“已提交”写成“已通过” |
| 确认弹窗 | 这个动作的后果，尤其不可逆的 | “确定要继续吗？”而不说继续会怎样 |
| 通知 | 跟用户有关的变化，需要做什么 | 为了拉活跃发无关信息 |

## 按钮

按钮用动词，说出具体的动作。“删除 3 个文件”比“确定”好；“付款 ¥128”比“提交订单”好。确认弹窗的两个按钮，最好一个是“删除”，一个是“保留”，而不是“确定”和“取消”，因为用户读到按钮时，可能已经忘了问题是什么。

## 错误提示

一个好的错误提示回答两个问题：**发生了什么？我能怎么办？**

> 文件超过 10 MB，没能上传。压缩一下再试试。
> The file is over 10 MB and wasn't uploaded. Try compressing it first.

- 不知道真实原因时，不要猜原因；能给的恢复动作才给。
- 不怪用户（“您输入了无效的……”），说清楚需要什么（“手机号是 11 位数字”）。
- 不在出错的时候开玩笑。用户正在着急。

## 状态要准

- 已提交 ≠ 已通过 ≠ 已完成。“申请已提交，等待审核”不能写成“申请成功”。
- 正在处理就说正在处理，可以的话给出大概多久。
- 不确定系统状态时，只写确定的那部分。

## 帮助文档和 FAQ

- 从用户要完成的事情写起。前提条件放在步骤之前。
- 界面名称、菜单、截图要和当前版本一致。
- FAQ 的问题最好来自真实的用户问题和客服记录。没有记录时，可以写“建议的 FAQ”，但不要宣称“用户最常问”。
- 答案第一句直接回答问题，再说条件和细节。“能退款吗”的答案不能是一段品牌理念。
- 步骤写法见 [explainer.md](explainer.md)。

## 发布说明和更新日志

- 先说变了什么、谁能用、在哪个平台。
- 还没发布的写“即将推出”，不写“现已上线”。
- 每一条从用户能做什么的角度写：“现在可以把评论导出为 CSV”，而不是“新增评论导出模块”。

## 社交帖子

社交帖子的读者在快速划过，所以开头很重要。但开头的作用是让对的人停下来，不是骗所有人点进来。

- **一条一个中心。** 读者划过时能抓住的只有一件事。
- **第一行说出最有意思的东西：** 一个结论、一个具体的数字、一个真问题。不用“家人们”“谁懂啊”开头，除非这就是账号的真实声音。
- **标题许诺的，正文要兑现。**
- **独立可读。** 帖子会被截图、转发、脱离上下文，涉及数据和主张的部分不要因此被误读。
- **长线程（thread）** 每条推进一步，而不是把一段话随便切开。

不同平台的习惯不同：

| 平台 | 习惯 |
|---|---|
| 微博、X | 短，观点鲜明，一条讲一件事 |
| 小红书 | 实用、亲身、图文并重；真实体验最有分量，最怕假装体验 |
| 朋友圈 | 私人语气，不要写成广告 |
| LinkedIn | 专业，但可以有个人视角；不要每句话都单独成段 |
| 公众号 | 可以长，但段落要短，开头三行决定读者走不走 |

不要堆 hashtag，也不要用 emoji 代替内容。

## 不同情境下的语气

同一个产品，在不同时刻说话的口气不一样：

- 用户第一次用：欢迎，告诉他们第一步做什么。
- 用户完成了一件事：简短确认，可以有一点温度。
- 用户出错了：平静、清楚、给办法。
- 用户付费失败、数据丢失：严肃、直接、负责，不要俏皮。

## 长度和显示

字数限制要来自真实的组件和平台。中英文、不同语言在同一个位置占的空间差别很大，要在真实界面上看截断和换行。只看文字，不能确认适配完成。

## 守住的东西

- 起草和改写可以做；发布、发帖、改线上内容需要用户授权。
- 用户只要文字时，交文字，不去动产品后台。
- 图标不能代替用户必须理解的状态，错误和动作信息要能独立读懂。可访问性是否达标需要专门检查。

# 翻译、本地化与中英 fusion

## 速用

先确认任务是忠实翻译、面向另一类读者重写，还是同一篇中的中英混用。翻译保留信息与语用功能；本地化可以调整惯例和呈现，但新增事实与承诺需要当前材料支持。只交用户要求的语言版本。

下列流程和例子为本 Skill 原创方法；它们使用 [Kane](../sources/kane.md)的读者、目的与准确措辞观念，不宣称 Kane 提供了中文翻译规范。读目标语言的对应节即可，不需为一次翻译加载两套全部参考。

## 开始翻译前保留什么

在心中或工作草稿里辨认数字、对象、条件、时态、否定、因果、程度、称谓、专名及关键术语。短句无需另建表。长文件反复出现且容易混淆的术语，可建立一份小术语表，不用为了流程列每个普通名词。

“可申请”“可使用”“可能有效”中的“可”分别涉及资格、能力、概率，英文译法应按含义选择。“shall”“will”“may”“should”的作用依文类判断；合同用语不能凭一般文风规则修改义务。

## 保意重组的例子

中文原句：“只对已完成审核的申请，系统才会发送通知。”
英文：“The system sends notifications only for applications that have completed review.”
若实际意思是审核通过，还需材料明确 approved；completed review 不自动等于 approved。

英文原句：“We plan to launch the feature in June, subject to security review.”
中文：“我们计划在六月推出这项功能，具体安排还取决于安全审查结果。”
不要改成“安全审查后将在六月推出”，原句没有保证六月可完成审查。

英文原句：“The team has not yet tested the mobile version.”
中文：“团队尚未测试移动版。”
不要补写“移动版暂时不能用”，未测试与不能用含义不同。

这些句子只说明语义处理。真实项目若有指定译法、法域要求或产品状态，须采用当前材料。

## 本地化可以改动的层面

称呼、礼貌方式、日期格式、单位呈现、大小写和句子顺序可按受众调整。换算单位时保留数值精度，明确是换算值；涉及合同、医学、财务或法规的字段，按该文件要求处理。

品牌原文中的笑话若依赖当地文化，可以提出替代方案；替代不应悄悄增加产品优势。中文品牌口号译成英文时可先保留核心信息，再选择节奏，不能把含蓄立场升级为绝对保证。

若用户要求逐句对照，就保持可对应性；若要求自然英文成稿，可以按段重组。关键术语、限定和引用仍需逐项核对。修改不清楚的原句时，应指出原意存在歧义，不能靠译文掩盖。

## 功能性 fusion

确定承载解释的主语言。保留 English 的常见理由包括：

- 它是用户实际看到的 UI、按钮、文件名或 API 字段。
- 它是领域内稳定使用、翻译后反而难辨认的术语。
- 它是需要准确呈现的短引语或讨论对象。
- 它表达了当前语境中有意义、中文近义词难以完整替代的区别。

例题给定界面按钮为 Export，格式为 PDF。
合适：“点击 Export，选择 PDF。”
不必要的混用：“我们可以先 review 一下，然后把整个内容做一个 polish。”若它是用户认可的口头声音，可按关系保留；面向普通公众的说明通常写“先检查内容，再修改表达”更容易理解。

API 字段、命令和文件名保持原样，不因中文排版插入全角符号。概念第一次出现时可写“retrieval（检索）”，后续按读者与篇幅选择一种稳定说法。不要每次都重复双语。

## 双语成品如何核对

核对两版是否使用同一对象、数量、时间与承诺。中文版的“部分用户”不能在英文版变成 users 的无条件泛指；英文版的 “reported” 也不应在中文版消失。不要要求两种语言句数相同。

标题可以为各语言重新安排重心，但仍要符合正文。双语 UI 还要看实际空间、截断与控件状态；只审文字无法确认真实界面容纳情况。

## 来源、引文与声音

引用原文和译文分别标示。自行翻译要写“译文”或按当前文档规范说明，不冒充已出版译本。未核官方译名时采用可识别的原名，并避免声称该译法由官方采用。

用户提供的经历只在获得授权的文稿中使用；语气样本可帮助判断节奏，不能借用其中事实。跨语言改稿可以保留直接、克制、幽默或细腻等写作选择，不复制某位作者的独特表达。

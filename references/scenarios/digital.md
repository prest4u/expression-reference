# UI、帮助内容、FAQ 与社交短文

## 速用

先判断读者此刻在做什么、系统实际发生了什么、文本放在哪里。界面文字需要与当前状态和可用动作匹配；社交短文需要独立可理解。篇幅短仍要保留改变判断的条件。

现代参照为 [Ann Handley, Everybody Writes（2014）公开书摘](../sources/books.md#bk-handley)。本文件的 UI 与渠道规则是原创应用，书摘不提供具体产品规范。产品界面、支持政策和平台限制须查当前材料。

## 按文本位置选择内容

| 位置 | 需要传达 | 常见错误 |
|---|---|---|
| 按钮 | 点击后发生的动作 | 用“确定”掩盖删除、付款或发送 |
| 表单说明 | 输入要求与用途 | 出错后才说格式要求 |
| 错误提示 | 失败状态与实际可用的恢复动作 | 一律写“出了点问题”，或乱归因网络 |
| 空状态 | 当前为何没有内容、可做什么 | 把没有记录写成系统故障 |
| 成功提示 | 已完成的具体动作 | 将已提交写成已批准 |
| 帮助页 | 适用条件、操作与结果 | 文档步骤和当前界面不一致 |
| FAQ | 一个实际问题的直接回答 | 用公司宣传替代答复 |
| 社交帖 | 可独立理解的观点或消息 | 为吸引点击省略关键条件 |

## 错误与成功消息

给定：文件超过 10 MB，系统没有上传，支持用户压缩后重试。
可写：“文件超过 10 MB，未能上传。请压缩文件后重试。”
英文：“The file exceeds 10 MB and wasn’t uploaded. Reduce its size and try again.”

这些数值与动作只属于例题。若实际失败原因未知，不能写超限；若重试不会解决问题，不建议重试。

给定：申请已提交、尚未审核。
可写“申请已提交，等待审核”。不能写“申请成功”造成获批误解。若系统没有明确排队状态，只写已提交。

## 帮助页与操作说明

从用户要完成的任务进入，必要前提放在操作前。步骤写清控件、动作和已知结果。截图、菜单名、权限和版本应与真实系统一致；只见旧文档时说明版本，不能推定现在未变。

把正常路径与常见异常分开，读者先完成当前动作；大量少见情况可用链接或可展开内容。真实复杂流程允许详细说明，不为了“极简”省去不可逆动作的结果。

## FAQ 的问题来源

优先使用真实用户问题、支持记录或产品流程中明确的疑点。没有记录时可以提出“建议的 FAQ”，不能宣称这些是用户最常问的问题。

问题应具体到一个可回答的内容。答案先回应，再提供必要条件和链接。不能把“是否能退款”回答成品牌服务理念。政策未知时需要查实际条款，不用写作参考编一套。

## 社交帖与发布说明

一条帖子通常围绕一个可理解的中心，必要上下文就近补充。长线程可以分段推进，但每条涉及数据或主张的内容应避免脱离上下文后误导。

功能发布说明先给发生的变化和适用条件。没有发布事实时，写计划或预览，不用“现已上线”。标题可以鲜明，正文应兑现所暗示的内容。点击率和互动率需要实际观察，不由文案风格推定。

## 原创发布例子

材料：桌面版新增评论导出为 CSV；仅管理员可用；移动版未提供。
中文：“桌面版现支持将评论导出为 CSV，管理员可使用这项功能。”
英文：“Admins can now export comments as CSV files in the desktop app.”

移动端未提供是否需在此处明说，取决于发布位置和读者误解的可能性。独立的通用产品页应让适用平台清楚；桌面版专属更新页已有平台上下文时可以更短。

## 内容与显示

字数限制须来自实际组件或平台。设计稿、界面实现和翻译可能有不同空间，需要看真实渲染后确认截断。不能只靠文字长度宣称适配完成。

图标不能替代用户必须理解的状态；错误和动作信息应能独立读懂。这里的建议帮助内容选择，真实可访问性是否合格仍需相应检查。

## 编辑与发送

文案可以在当前授权范围内起草和改写；发布、发消息或改线上内容需要相应授权。用户只要文字时交文字，不擅自操作产品后台。自然语气来自清楚和合乎情境，不需要给报错加俏皮话。
